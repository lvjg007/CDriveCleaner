# 安全清理与状态透明化设计

## 背景

产品当前已经能扫描并清理多类缓存，但执行层仍允许报告类系统文件被反选删除；部分目录项的失败会被汇总成成功；扫描或清理取消后，界面仍显示普通完成。下一轮先修复这些会直接影响误删风险和用户判断的问题。

## 目标

1. 执行层无论来自哪条 UI 路径，都拒绝删除报告类系统文件、受保护目录和符号链接目标。
2. 扫描结果明确区分完整扫描、快速扫描和用户取消；取消的扫描结果不能启动清理。
3. 清理结果记录取消状态、未处理数量和失败信息，界面摘要能让用户定位失败。
4. 用自动化测试覆盖保护、取消和状态同步；保持现有扫描器 API 不变。
5. 扫描器达到时间上限时传递结构化分类状态，UI 显示部分结果并在清理确认中保留提醒。

## 方案

在 `CleanItem` 增加显式 `deletable` 与保护原因，Space Hogs 直接生成不可删除项；路径层提供集中式 `is_deletion_protected`，覆盖硬排除、C 盘系统占用文件、用户字体目录、项目目录和符号链接。执行器先做 item 与 path 双重校验。

`CleanResult` 增加 `cancelled` 和 `remaining_count`。`Orchestrator` 保留既有返回值，同时记录 `last_scan_cancelled`、`last_scan_fast`，UI 依据这些状态显示“已取消/快速扫描完成”，取消扫描时禁用清理按钮。结果表增加管理员权限列，清理摘要显示前几条失败路径和原因。

扫描超时通过共享扫描上下文记录当前 scanner 的部分结果分类。底层 `dir_size`/`safe_iter_files` 和有独立 deadline 的扫描器都写入该上下文；编排层汇总为 `last_scan_partial_categories`，UI 将其显示为“扫描完成（部分结果）”，清理确认附带不完整提示。

## 非目标

- 本轮不重写所有扫描器的目录粒度；整棵应用数据目录拆分为缓存子目录单独迭代。
- 不改变永久删除、回收站和模拟清理的既有入口。
- 不引入新依赖，不要求真实 Tk 窗口测试。

## 验收标准

- Space Hogs、系统占用文件、字体目录、项目目录和符号链接均无法被执行器删除，并产生失败原因。
- 预置取消标志时扫描/清理不再继续，结果状态准确记录。
- 现有 30 项测试与新增回归测试全部通过。
